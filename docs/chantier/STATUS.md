## Comment travailler à plusieurs sans collision

1. **Lire ce fichier sur `main` et les PR ouvertes avant d'agir.** Ne pas reprendre une tâche déjà attribuée sans transfert explicite. Ne jamais interpréter une vieille section « terminé » comme preuve actuelle.
2. **Réserver une tâche avant le premier changement de code** : une seule ligne active avec ID issue/PR, propriétaire (`GPT`, `Sonnet`, `Opus`), périmètre/chemins concernés, branche, statut et prochaine action. Pas de double propriétaire actif. Si l'assignation est inconnue, inscrire `à attribuer` plutôt que deviner.
3. **Mettre à jour après chaque événement vérifié** : début, PR ouverte, blocage, changement de propriétaire, checks, merge. `FAIT` exige une PR effectivement fusionnée dans `main` (ou une preuve précise si aucun code n'était à livrer). La certification staging/production est un verdict séparé.
4. **Chaque agent met à jour les chantiers auxquels il a contribué, même si la tâche appartient à un autre.** GPT, Sonnet et Opus doivent consigner eux-mêmes toute intervention effective (analyse, correction, test, revue, déblocage, commit, fusion) sur la **ligne existante** : `intervenant + action + lien de preuve + résultat + prochaine étape`. Mettre à jour aussi la `## Reprise` de la PR si pertinente et informer le propriétaire dans la PR/issue. **Ne jamais changer le responsable unique par simple contribution** ; seul un transfert explicite le modifie. L'obligation de journaliser n'autorise pas une prise de contrôle du code d'autrui.
5. **Ne pas se marcher dessus** : une tâche = un propriétaire à la fois ; scope technique et fichiers clairement indiqués ; pas de changement de même writer, migration ou contrat transversal en parallèle sans coordination. Si conflit de périmètre, mettre en `BLOQUÉ` et signaler.
6. **Pas d'écrasement concurrent de STATUS.md** : relire la version la plus récente sur `main` avant chaque écriture ; faire une modification minimale, conserver les lignes d'autrui ; utiliser le SHA de fichier / rebase, et en cas de conflit relire et recomposer, jamais forcer. Une modification de coordination passe par le workflow Git prévu par `AGENTS.md` ; ne pas court-circuiter ses gates.
7. **Éviter la bureaucratie** : une ligne courte par chantier actif ; lien issue/PR ; tests/checks et commits précis. Les détails, discussions et preuves longues restent dans les PR. Archiver les tâches closes hors du tableau actif après une période raisonnable, avec le lien de preuve. Pas de second tracker dans `.agent/`, `docs/Work/` ou des prompts.

Statuts autorisés : `À_FAIRE` · `EN_COURS` · `PR_EN_REVUE` · `BLOQUÉ` · `FAIT` · `ABANDONNÉ`. Une PR draft ouverte n'est pas `FAIT`.
