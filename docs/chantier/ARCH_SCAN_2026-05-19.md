# ARCH-SCAN-1 — Scan architectural backend

> Date : 2026-05-19  
> Scope : documentation uniquement  
> Branche de référence : `main`  
> Objectif : identifier les zones architecturalement faibles avant d'enchaîner les refactos.

---

## 1. Verdict exécutif

Le backend n'est plus en situation de feu métier critique : les lots I-SWEEP et TEST-1A/1B ont traité les principaux risques fonctionnels autour des flows G1-G5.

En revanche, l'architecture reste fragile sur certains axes :

```text
1. server.js concentre trop de responsabilités.
2. Les très gros fichiers métier restent nombreux.
3. Le logging est dispersé en console.*.
4. Les migrations inline/post-boot et historiques SQL restent difficiles à gouverner.
5. Les domaines pricing/dashboard sont probablement les prochains gros blocs à isoler.
```

Conclusion : il est utile de continuer la refacto, mais uniquement par lots petits et testables.

## 4. Classement architectural par risque

### A. Zone rouge — à traiter par priorité contrôlée

| Zone | Problème | Risque | Décision |
|------|----------|--------|----------|
| `server.js` | Trop de responsabilités : env, security, webhooks, routes, HTML, crons, migrations, listen | Risque de casser boot/webhooks/routes en cas de changement opportuniste | Continuer H1 par étapes, commencer par H1A-2 local |
| Webhooks Stripe raw body | Dépendent strictement de l'ordre avant `express.json` | Rupture paiement si déplacés | Ne pas déplacer avant test dédié |
| Migrations inline post-boot | DDL runtime + historique SQL séparé | Difficulté de gouvernance DB et risque au refacto | Ne pas déplacer avant P0 runtime PASS ou lot H1F séparé |
| `console.*` dispersés | Logging non structuré, bruit Railway, absence de niveaux/contextes | Debug production fragile | Lancer F1A pilote après H1A-2 ou en parallèle prudent |

### B. Zone orange — refacto utile mais pas immédiat sans tests

| Zone | Problème | Risque | Décision |
|------|----------|--------|----------|
| `routes/dashboard.js` | Probable god-route / agrégateur de stats | Couplage élevé, modifications risquées | Planifier B3 REFAC-dashboard après H1A/P0 |
| `services/pricing-engine.js` | Moteur économique dense | Régression marge/pricing si découpe mal testée | Ne pas refactorer avant tests comparatifs stricts |
| `routes/pricing.js` + services pricing | Domaine critique I-08 | Risque sur prix et survival | PRICE-1 seulement si P0/staging révèle un problème |
| `routes/products.js` | Publication catalogue + audit prix/stock | Risque catalogue si refacto opportuniste | Garder stable, compléter tests si changement |
| `routes/purchasing.js` | Trigger POs + réception | Risque fournisseur / doublons | Ne toucher que sous test transactionnel |
| `routes/scans.js` / pickup | Retrait, preuves, QR | Risque confiance opérationnelle | Ne pas refactorer hors lot dédié |

### C. Zone jaune — dette de rangement / hygiène

| Zone | Problème | Décision |
|------|----------|----------|
| Scripts/audits mal placés | Chemins confus | H3 plus tard |
| Docs anciennes / prompts historiques | Risque de relancer vieux lots | Garder archive + kit post-critique actif |
| Migrations 060/061 | Collisions documentaires | A4 clôturé diagnostic ; ne pas renommer maintenant |

## 5. Réponse à la question : H1A reste-t-il le bon prochain lot ?

Oui, mais avec une nuance.

H1A-2 reste le meilleur prochain lot de refacto **si et seulement si** il est appliqué via le codemod local déjà préparé, avec vérification du diff et tests.

Pourquoi H1A-2 reste prioritaire :

1. `server.js` est le nœud central de risque architectural.
2. H1A-0 et H1A-1 sont déjà prêts.
3. H1A-2 a un périmètre limité : routes API standards seulement.
4. Les zones dangereuses restent hors scope : webhooks raw, parsers, HTML, crons, migrations.
5. Le gain est réel : réduire la surface de `server.js` sans toucher au métier.

H1A-2 ne doit pas être fait via remplacement manuel complet de `server.js` dans GitHub.

## 6. Ordre de refacto recommandé

### Étape 1 — sécurisation immédiate

```text
H1A-2 : appliquer le codemod server.js localement
```

Commandes attendues :

```bash
node scripts/h1a-wire-api-routes.js --check
node scripts/h1a-wire-api-routes.js --write
git diff -- server.js
npm test
npm run test:p0
```

PR attendue : uniquement `server.js` si le diff est propre.

---

### Étape 2 — décider entre H1B et F1A

Après H1A-2 :

```text
Si boot/tests OK → H1B ou F1A.
Si logs restent ingérables → F1A.
Si server.js reste encore trop lourd → H1B.
```

Recommandation : F1A peut être fait juste après H1A-2, car le logging structuré améliore toutes les validations suivantes.

---

### Étape 3 — gros domaines métier

Ne pas attaquer dashboard/pricing avant :

```text
1. H1A-2 terminé ;
2. P0 runtime au moins exécuté localement ;
3. tests ciblés ajoutés pour le domaine concerné.
```

Ordre recommandé :

```text
B3 REFAC-dashboard avant B2 REFAC-pricing
```

Raison : le pricing touche directement I-08 et la marge ; il demande des tests comparatifs plus stricts.

---

## 7. Ce qu'il ne faut pas faire

Ne pas :

- lancer une refonte globale de `server.js` ;
- découper `pricing-engine.js` sans test comparatif ;
- découper `dashboard.js` et `server.js` dans la même période sans stabilisation ;
- remplacer tous les `console.*` en une seule PR ;
- déplacer les migrations inline avant un lot H1F dédié ;
- déplacer les webhooks raw sans test prouvant la conservation du raw body.
